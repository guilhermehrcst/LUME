# E2 code generation audit (POST HOC)

Question: E2 found a non-monotone N profile and a compiler-dependent best threshold. Before attributing either to the memory hierarchy, do the Materialize (M) and Recompute (R) loops compile to comparable code, and is there any size-dependent code path?

Scope and method. The executor translation unit (`src/runtime/cpu_reference.cpp`) was compiled with the primary E2 configurations, `-O3 -DNDEBUG -std=c++20`, GCC 13.3 and Clang 18.1, no `-ffast-math`, no `-march=native` (so the x86-64 baseline, SSE2). Vectorization reports (`-fopt-info-vec-all`, `-Rpass*`) and `objdump -d` were inspected; the tooling is `experiments/e2-materialize-vs-recompute/codegen_report.{sh,py}`; evidence is in `e2-results/audit/codegen/`. Claims are classified OBSERVED (read from the compiler output or disassembly), INFERRED (reasoned, not tested) or UNKNOWN. Nothing about cache traffic is inferred from assembly.

Kernels: M = `add_buffers` (fresh result: 2 loads, 1 add, 1 store per vector) and, for the last consumer, `add_in_place` (destination is an operand: read-modify-write); R = `add_add` (fused: 3 loads, 2 adds, 1 store per vector).

## Findings

| # | claim | class |
| --- | --- | --- |
| 1 | Every M and R loop is vectorized on both compilers; f32 uses `addps`, i32 `paddd`; 128-bit SSE2 registers only (0 `ymm`/`zmm` instructions in either object). | OBSERVED |
| 2 | GCC: one 128-bit vector per iteration (4 elements); M loop = 2 loads, 1 add, 1 store; R fused loop = 3 loads, 2 adds, 1 store; no unrolling of the vector loop. | OBSERVED |
| 3 | Clang: loops unrolled by 2 vectors per iteration (8 elements); M = 4 loads, 2 adds, 2 stores per iteration; R fused = 6 loads, 4 adds, 2 stores. | OBSERVED |
| 4 | Loads and stores are unaligned (`movups`/`movdqu`); there is no alignment peeling and no alignment dispatch. | OBSERVED |
| 5 | Vector main loop is preceded by a runtime trip-count guard: GCC skips its 4-wide loop for n <= 3 (handled by shorter code), Clang skips its 8-wide loop for n < 8 (scalar). GCC additionally runs a vector 8-byte (2-element) epilogue then a scalar tail; Clang uses a scalar tail unrolled by 4 with a run-time trip count. N = 64 and above always enter the vector loop. | OBSERVED |
| 6 | GCC versions the loops for possible aliasing (the report says "loop versioned for vectorization because of possible aliasing"): a runtime distance check of result against each input, falling back to a scalar loop. Clang's fused kernel has no alias check (fresh `operator new` result); the fresh-result `add_buffers` loop that was inspected carries a runtime overlap check (distance >= 32 bytes); the in-place loops were not individually inspected for checks. Whether the fallback paths ever execute in E2 was not instrumented. | OBSERVED (code), UNKNOWN (executed) |
| 7 | There is no size-dependent dispatch other than the trip-count guards above: no non-temporal stores, no prefetches, no `rep movs`/`rep stos`, no calls to `memcpy`/`memset`/`memmove` in either object. The code executed for N = 16 Ki is the same loop as for N = 16 Mi. | OBSERVED |
| 8 | Consequently the non-monotone N profile (e.g. R catching up at N = 64 Ki and 4 Mi) is not explained by any code-path change between those sizes. Its cause is not established by this audit; cache/associativity/allocator/page effects remain candidates. | INFERRED (by elimination of code paths only) |
| 9 | M and R are generated by the same compiler with the same instruction set and the same loop shape class (straight-line vector loop, scalar tail). No code-shape asymmetry that would systematically favour one strategy at all N was found; the difference in vector work per element is the intended one (R: 3 loads + 2 adds + 1 store per vector; M: 2 loads + 1 add + 1 store per vector, plus one extra pass for D). | OBSERVED |
| 10 | GCC and Clang differ in unroll factor (1 versus 2 vectors per iteration), epilogue style and alias handling. This is a plausible contributor to the compiler-dependent best threshold (T = 1 versus 2) and the 10 % winner disagreement, but the contribution was not measured. | INFERRED |
| 11 | Absolute performance of the loops relative to hardware limits, cache residency, and store/load traffic at each N. | UNKNOWN |

## Consequence for E2

No implementation bias that invalidates M versus R was found. The codegen audit rules out size-dependent code paths as the explanation of the N profile, and does not identify the cause. The next evidence needed is a hardware performance-counter characterization on a physical machine (E2-R1).
